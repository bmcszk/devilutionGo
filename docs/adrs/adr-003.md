# 003. SQLite-only live saves with one-time importer

Date: 2026-10-16
Status: Accepted; the one-time importer surface stays, but its entry point becomes the `saves` subcommand of devilutionGo-migrate (ADR-014) instead of a stand-alone devilutionGo-import command; text below is unchanged

## Context

devilutionX saves are binary .sv/.sp files. The port needs a Go-native store, but existing saves and byte-level compatibility matter to users.

## Decision

SQLite is the only live save format. One hero = one .db file, mirroring the per-hero .sv model. A separate global.db holds stash and metagame state. A one-time CLI tool (devilutionGo-import old.sv) converts legacy saves and proves byte-compat. No dual-format live writes.

## Consequences

No code path writes .sv. Import correctness is tested against real saves. Settings are NOT in SQLite (see ADR-004).

Save-story precedence, mirroring upstream demo-vs-save validation (`Source/pfile.cpp:657` `pfile_write_hero_demo`, `Source/pfile.cpp:665` `pfile_compare_hero_demo`, `Source/engine/demomode.cpp:958` and `:970`; line anchors grep-verified 2026-11-13 at fork commit `e1ad0c2b6`): the SQLite rows written by the `SaveHero`/`SaveGame`/`SaveLevel` store layer are THE session save, the only thing a mid-dungeon restore loads. The tick log living in the same store is the replay and desync oracle, validated against those rows the way upstream validates a demo replay against the reference hero save; snapshot plus replay is verification, never a competing loader. See [ADR-018](adr-018.md) law 4 (the log is the game) for the event-model side of the same decision.
