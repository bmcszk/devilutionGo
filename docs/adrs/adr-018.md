# 018. Everything is an event: commands in, events out

Date: 2026-11-03

## Status

Accepted (2026-11-03). Extends ADR-015 (deterministic simulation kernel).

## Context

The idea: everything that happens in the game is an event. A player click, a monster
dying, a door opening, a buff ticking. ADR-015 already says commands go in and events
come out, but it does not push that idea across the whole game, and it does not name
the failure modes. This ADR confronts the idea and decides how far it goes.

Research says the idea is proven at scale. Shipped games run this way:

- Age of Empires ships "1500 archers" lockstep: the wire carries only player commands,
  and the same commands drive replays and desync hunts (AoE team talk, Meeting C++
  2026; the original 1500 Archers paper).
- Factorio: "all multiplayer peers will calculate the simulation themselves and only
  the player input (we call it input actions) will be exchanged over the network"
  (Friday Facts #30). Factorio's early multiplayer months were mostly desync triage
  (Friday Facts #188), which is the price of this design.
- DevilutionX, the origin of this port, already runs deterministic lockstep with a
  command-only wire and per-tick AI seeds (verified in earlier research for ADR-015).
- OpenTTD commands are the same log as replays. A desync report shows the checksum
  mismatch per company, sync traces diff to the first divergent write, and a replay
  after the fix proves the repair (OpenTTD Desync Documentation).
- A small 2026 lockstep game (battledrones) hashes the world every 10 ticks; on
  mismatch it publishes the seed, settings, full command log, and both hash trails,
  so the bug replays exactly (MULTIPLAYER.md in that repo).
- Unreal's Gameplay Ability System builds abilities and effects on gameplay events;
  central event tags replace scattered cross-module calls (Epic docs, community
  guides).
- Spring RTS records a per-write trace and diffs it to find the first divergence.

Research also says what breaks when teams take "everything is an event" too far:

1. Dangling references. Listeners outlive their owners. Go's event libs guard with a
   mutex plus a nil check; Nystrom's Event Queue needs an explicit clear-all API.
2. No order. "Bevy does not provide a way to specify the relative ordering of
   observers watching for the same event. Their ordering is considered to be
   arbitrary" (Bevy Observer docs). Unordered mutators cannot live in a
   deterministic kernel.
3. Fire everything, gate nowhere. A saturated bus wakes every listener. Cure: gate or
   discard cheaply at the edge (Nystrom: save cycles by not processing work you do
   not have to).
4. Feedback loops. Handlers that publish new events can cycle forever. Nystrom:
   avoid sending events from within code that is handling one, unless the design
   budgets the depth.
5. Opaque flows. "Overuse leads to invisible flows that are hard to trace" (event
   driven gameplay write-ups). Cure: typed payloads, per-domain scopes, subscription
   logging at load.
6. A bus is not a save game. "The real saving grace of an event system is the ability
   to log all events in a central place" (Nystrom). The replay and the save need the
   durable log, not the in-memory bus.
7. Replay cost grows with the log. "Rebuilding a projection from millions of events
   can take hours" (event sourcing engineering write-ups). Snapshotting on a cadence
   is the standard cure.

Two verified library facts pin the design:

- Watermill GoChannel: default Publish does not block and sends in the background.
  With BlockPublishUntilSubscriberAck=true, Publish waits until subscribers Ack.
  Even in blocking mode, each subscriber runs in its own goroutine, and
  cross-subscriber order is not guaranteed. Persistent mode does not guarantee
  order either (pkg.go.dev, watermill.io, DeepWiki). So the kernel must call handler
  chains itself, in registered order, and Watermill must never host sim-mutating
  handlers.
- donburi ships a typed events feature with an explicit ProcessEvents step, so
  handlers run at a known time and can keep world access without locks (pkg.go.dev).

Verdict: adopt the idea everywhere, with ordered dispatch and a durable log as the
rails that keep it alive.

## Decision

The event model covers the whole game through six laws.

1. Commands in. Everything that wants to change the game sends a command: player
   input, AI, timers, quests. A command is data with a tick number. Handlers never
   run late; late work waits for the next tick. The kernel is the only code that
   applies commands to state.
2. Events out. Every state change emits an event: MonsterDied, SpellCast,
   ItemPickedUp, DoorOpened. Handlers subscribe; nothing polls. Presentation,
   sound, and achievements read events and never write game state. Client
   predicted events are display only.
3. One ordered pass per tick. The kernel drains the command queue once per tick,
   in order, and each handler chain runs in registered order inside the tick. One
   tick, one state pass, no locks in sim code, one replayable story. Handlers read
   freely, write only their own slice, and request wider change by command.
4. The log is the game. The tick log is the save. Save = header + snapshot + the
   tick log after it. Load = header + snapshot + replay, then live play. Netcode,
   replays, desync checks, and headless tests all read the same log. The kernel
   snapshots every 1,000 ticks; the cadence is tunable in settings. The tick log
   and its snapshots live inside the SQLite store per ADR-003; the log is not a
   second save format, it is one column family of the same store. Precedence between
   the log and the row data is fixed in the [ADR-003](adr-003.md) save-story paragraph:
   rows save, the log is the replay/desync oracle validated against rows.
5. The bus stays small. Command and event types live in one package with domain,
   verb, past tense names. The kernel owns dispatch order. Watermill GoChannel
   (ADR-015, go-libraries.md) carries the fan-out to presentation. No
   sim-mutating handler ever subscribes to Watermill, because GoChannel gives no
   cross-subscriber order.
6. Gate at the edge. The gate drops commands that cannot change anything: out of
   range, dead target, not enough mana, cooldown running. Events fire only when
   state actually changes, and nobody subscribes, the event dies at publish.

| Role          | Reads            | Writes            | Notes                          |
| ------------- | ---------------- | ----------------- | ------------------------------ |
| Gate          | player, AI intent | nothing          | drops invalid commands early   |
| Handlers      | state, own slice | own slice         | emit events, request commands  |
| Kernel        | everything       | everything        | one ordered pass per tick      |
| Watermill bus | events           | nothing           | fan-out to presentation only   |
| Presentation  | events           | display state     | never sim state                |

The ARPG framework ships these six laws as code. Diablo 1 ships content: monster
tables, spells, items, and the event names the original touches. Grilling decisions
for the whole-game conversion live in the milestone bean
[devilutionX to Go+Ebiten+SQLite whole-game conversion](../../.beans/devilGo-i56j--devilutionx-goebitensqlite-whole-game-conversion.md).

## Consequences

Positive:

- One story covers every action: intent, gate, ordered tick, event log. Tests and
  bug hunts follow that story instead of scattered update calls.
- Replays, save games, netcode, desync hunts, and headless runs read one log. This
  pairs with ADR-017: the same kernel runs headless and captures frames or audio.
- Desyncs produce evidence: a checksum per tick plus the log to replay and bisect
  (battledrones and OpenTTD patterns).
- New content plugs in as tables plus handlers. Presentation stays swappable
  because it only reads events.

Costs, accepted with mitigations:

- The log grows and replay cost grows with it. Mitigation: snapshot every 1,000
  ticks, prune old logs per settings, cap consumed slices.
- Listener lifetime bugs (dangling references) show up late. Mitigation:
  unsubscribe guards on teardown, clear-all in tests, subscription logging at
  level load.
- Handler chains can hide flows. Mitigation: typed payloads, one package for
  names, logged subscriptions.
- Feedback loops need a budget. Mitigation: handlers emit after their slice
  settles, never mid-chain by default; debug builds detect runaway cycles.
- Every tick pays for the ordered pass. Mitigation: the gate and typed handlers
  keep the pass cheap; it stays small next to rendering.
