# 015. Deterministic fixed-tick simulation

Date: 2026-11-03
Status: Accepted (2026-11-03)

## Context

The original game runs in fixed time steps, and in multiplayer only player commands cross the network; every machine that applies the same commands ends up with the same game state. ADR-002 requires identical algorithms and random number behavior. The game must also run headless and stay reusable for other games.

## Decision

The code in game/ holds a deterministic simulation. It advances in fixed ticks like the original. Player actions arrive as commands, handlers run in a fixed order, and events go out to the screen code. Events predicted on the client are display only; they never change the real game state. Random numbers come from separate seeded generators (item drops, per-tick AI, attacks, item wear) the way the original uses per-tick AI seeds. Simulation math uses the original's integer math; float64 stays out of game state and per-tick gameplay paths. Lighting falloff tables are precomputed once at startup, mirroring the original's single sqrt in table build (see docs/lighting.md). Tests and lint ban wall-clock reads, extra threads, and loops that walk map entries in unstable order inside the sim packages. Events and state views, not commands, reach the screen: player intents reenter only through commands (watermill in-process bus fans events out to presentation; the kernel itself drives the handlers, per ADR-018 law 3 and 5). Tests record game replays and compare state checksums at fixed tick counts (extends ADR-010).

## Consequences

Single player is multiplayer with one player. Every game session already produces a replay and a desync check, and headless testing needs no window.
