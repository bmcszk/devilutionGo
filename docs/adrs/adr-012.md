# 012. SQLite driver: modernc.org/sqlite (pure Go, no CGO)

Date: 2026-11-02
Status: Accepted

## Context

ADR-001 fixed the stack at "pure Go: no CGO anywhere, including drivers
and codecs" and ADR-003 made SQLite the only live save format, but the
concrete driver choice was asserted without a record. The wave-3
persistence port (PR #11) pins `modernc.org/sqlite v1.34.4` in go.mod;
this ADR records why it over the alternatives.

The Go ecosystem has three maintained SQLite drivers:

- **modernc.org/sqlite** — the SQLite C amalgamation machine-translated
  to Go; `database/sql` driver; no CGO; BSD-3-Clause.
- **github.com/mattn/go-sqlite3** — bundled SQLite C amalgamation via
  CGO; MIT.
- **github.com/ncruces/go-sqlite3** — SQLite compiled through Wasm and
  translated with wasm2go; no CGO; MIT.

## Decision

`modernc.org/sqlite`, imported by its canonical module path. The
canonical source is GitLab `cznic/sqlite`; `github.com/modernc-org/sqlite`
is the project's mirror (issues/PRs accepted there, merged into GitLab)
and `pkg.go.dev/modernc.org/sqlite` is the module — one import path for
go.mod regardless of which repo a web search lands you on.

## Alternatives considered

**github.com/mattn/go-sqlite3** — rejected on the ADR-001 hard rule:
SQLite runs in-process during gameplay (20 Hz tick writes hero/level
state through the persistence port), and CGO drops the goal of a
toolchain-only build (no gcc per platform, trivial `GOOS=GOARCH`
cross-builds, no C flags in CI). mattn is also the slowest of the three
on this workload's mix per published 2026 benchmarks, and it drags
cgo,labs/goyacc-sized dependency trees.

**github.com/ncruces/go-sqlite3** — rejected on the same no-CGO-free
basis (it is CGO-free) but with a different cost: a Wasm runtime in the
binary for a game that already vendors a JIT-free interpreter budget;
its VFS layer and wasm2go translation pull in a larger runtime surface,
and the upstream track record for our workload is thinner (fewer
production users than modernc). It's a strong second for very-embeddable
SQLite feature parity (custom VFS, backup API), none of which we use.
Not chosen.

## Consequences

- One less C toolchain: `go build ./...` and `just lint` stay hermetic
  with zero CGO env vars.
- CPU-bound SQLite work is measurably slower than mattn's C amalgamation
  (WAL mode, 10k-row benchmark mix). We accept ~1.5-2x slower than C on
  write-heavy loops because our writes are occasional, batched, and
  conflict with zero other readers during tick synchrony (single save
  transaction per tick or per level transition, `SetSaveContext`).
- Pin drift risk: modernc.org/sqlite pins `modernc.org/libc`, and the
  couple can be fragile at minor boundaries; we upgrade deliberately and
  re-run the full persistence suite (`just lint`, `go test ./internal/persist/...`)
  on each bump.
- License: BSD-3-Clause, compatible with the repo's distribution. mattn
  and ncruces are MIT — parity was a tie, not a differentiator.
