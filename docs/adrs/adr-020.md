# 020. Two binaries

Date: 2026-11-05
Status: Proposed (2026-11-05)

## Context

`cmd/` holds four commands today: `devilutionGo`, `devilutionGo-headless`,
`devilutionGo-migrate` and `gamedatagoldens` (`cmd/` directory). The project
tells users a different story.

* ADR-019 says `devilutionGo-migrate` is the one conversion program
  (`docs/adrs/adr-019.md:38-40`) and that its refresher tooling is test
  instrumentation, not a conversion tool (`docs/adrs/adr-019.md:71-84`).
* ADR-017 already describes one program with three run modes, `sim`, `server`
  and `client` (`docs/adrs/adr-017.md:10-12`). Nobody runs a second executable
  to change mode.
* `devilutionGo-headless` is the same game loop with a different entry point:
  it drives the tick loop with `engine.MockTickSource` and one flag,
  `--ticks` (`cmd/devilutionGo-headless/main.go:35-48,:55-57`). The GUI
  command builds the same `game.NewGame` and reads its own flag
  (`cmd/devilutionGo/main.go:14-16`). Two `main` packages share one game.

So the extra headless binary buys no code separation. It costs a second build
recipe (`justfile:10`), a second build tag, and a second name
(`docs/recipes/justfile-patterns.md:23`).

`gamedatagoldens` is a different case. It regenerates committed golden JSON
from committed TSVs (`cmd/gamedatagoldens/main.go:22,:26`) and runs from
`just refresh-gamedata-goldens` (`justfile:64`). It never builds devilutionX,
reads an MPQ or touches the network (`tools/probe/README.md:117-122`). ADR-019
already lists it as a fixture refresher, not a conversion tool
(`docs/adrs/adr-019.md:81-84`).

## Decision

The project ships exactly two user-facing binaries:

1. **`devilutionGo`** is the game. Headless mode becomes a command-line
   parameter of this one binary, for example a `--headless` flag or a
   `headless` subcommand. The tick budget `--ticks` travels with it
   (`cmd/devilutionGo-headless/main.go:57`). This matches the run-mode split
   ADR-017 already chose (`docs/adrs/adr-017.md:12`).
2. **`devilutionGo-migrate`** is the one conversion program. ADR-014
   (`docs/adrs/adr-014.md`) and ADR-019 (`docs/adrs/adr-019.md:38-40`) set
   that; this ADR keeps it.

Classification of the four commands in `cmd/`:

| Command today | Class | Target |
|---------------|-------|--------|
| `cmd/devilutionGo` | user-facing, game | stays, gains the headless parameter |
| `cmd/devilutionGo-headless` | user-facing, game | folds into `cmd/devilutionGo` |
| `cmd/devilutionGo-migrate` | user-facing, conversion | stays, unchanged |
| `cmd/gamedatagoldens` | test instrumentation | leaves the user-facing set |

`gamedatagoldens` is a fixture refresher under the ADR-019 carve-out
(`docs/adrs/adr-019.md:71-84`, `tools/probe/README.md:85-91`). It is not a
conversion binary and users never run it, so it does not count as a third
binary. Its final home belongs to the devkit and test-instrumentation surface,
next to `tools/probe/dunconv` and `tools/probe/affix_probe`. Whether that home
is a move under `tools/` or a deletion is decided when the work runs.

## Consequences

**Users see two binaries, not four.** `devilutionGo` runs windowed or
headless from one entry point. `devilutionGo-migrate` converts. Nothing else
in `cmd/` is for users.

**Nothing is removed yet.** This ADR records direction. It deletes nothing and
moves nothing. Execution lands in follow-up beans: one folds
`devilutionGo-headless` into `devilutionGo`, one relocates `gamedatagoldens`.
Until those beans land, the four commands in `cmd/` keep building as they do
today, and no document should claim otherwise.

**The fold keeps one test surface.** `cmd/devilutionGo-headless/main_test.go`
covers the tick loop, the exit codes and the app-fatal boundary
(`cmd/devilutionGo-headless/main_test.go:1-30`); that file follows the code
into `cmd/devilutionGo`.

Renaming a shipped binary breaks scripts, so `just build-headless`
(`justfile:10`) stays until the fold bean retargets it to the one binary.

**Removed:** nothing. No command, recipe or fixture changes in this ADR.
